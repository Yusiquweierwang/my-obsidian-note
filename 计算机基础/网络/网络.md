### WebSocket

#### websocket是http协议吗
**不是。** WebSocket 是独立协议(RFC 6455)。它只是"借道"HTTP 来握手:

- 建立连接时,浏览器先发一个 HTTP 请求,带 `Upgrade: websocket` 头
- 服务器同意后,这条连接就"升级"成 `ws://` 协议
- **升级之后就和 HTTP 没关系了**,走的是独立的双向 TCP 长连接

HTTP 是"**一问一答**"——客户端问一次,服务器答一次,结束。WebSocket 是"**一条热线**"——连上后,双方随时可以互相发消息,服务器能主动推给你。

**那为什么不是 MQTT?核心在这:**

两者不在同一层:

||WebSocket|MQTT|
|---|---|---|
|属于哪层|**传输层**(怎么保持连接)|**应用层消息协议**(怎么按主题收发)|
|给谁用|浏览器/前端|物联网设备(传感器、无人机)|
|浏览器原生支持|✅ 原生支持|❌ 不支持,得靠库再套一层|

**关键点:浏览器里跑的是 JavaScript,它原生只能建 WebSocket 长连接,不能直接连 MQTT。**

MQTT 是设计给**设备端**(无人机、传感器)用的——轻量、低带宽、弱网也能扛。而你的低空航图要在**浏览器里用 Cesium 渲染**,前端收实时数据只能靠 WebSocket。

**所以真实架构里,这俩其实是接力用的,不是二选一:**

```
无人机/传感器  →  MQTT(设备端,轻量弱网)  →  消息中间件Broker
                                                        ↓
        浏览器前端(Cesium渲染)  ←  WebSocket(浏览器全双工)  ←  后端推送
```

- **数据源头**(无人机回传遥测、雷达数据):用 MQTT,设备端资源少、网络差,MQTT 最合适
- **后端 → 浏览器前端**:用 WebSocket,因为前端只能靠它保持双向长连接
- 中间如果设备数据也要进浏览器,常见做法是"**MQTT over WebSocket**"——用 WebSocket 把 MQTT 协议包起来传,本质还是 WebSocket 这条线



#### websocket如何建立连接
1.客户端发起升级请求（HTTP）
	浏览器先发一个普通的 HTTP GET,但带了几个特殊头,告诉服务器"我想升级成 WebSocket":

```http
GET /chart HTTP/1.1
Host: example.com
Upgrade: websocket              ← 要求升级协议
Connection: Upgrade             ← 声明这是升级
Sec-WebSocket-Key: x3JJHMbDL1EzLkh9GBhXDw==   ← 随机16字节的base64
Sec-WebSocket-Version: 13       ← 协议版本号
```
2.服务器回"101 切换协议”
	服务器理解后,返回状态码 `101 Switching Protocols`,并回一个计算出来的值:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: HSmrc0sMlYUkAGmm5OPpG2HaGWk=   ← 根据上面的Key算出来的
```
3.握手完成
	TCP连接不再走HTTP，升级成独立的WebSocket协议。之后数据以"帧(frame)"形式双向传输,不再是"请求-响应"。


### TCP/IP


|层|名字|干的活|你前面问过的东西|
|---|---|---|---|
|第4层|**应用层**|定义"数据长什么样、怎么组织"|HTTP、HTTPS、DNS、GET/POST 方法|
|第3层|**传输层**|定义"数据怎么可靠地送到"|TCP、UDP、**端口号**|
|第2层|**网络层**|定义"怎么跨网络找到目标机器"|**IP 地址**|
|第1层|**网络接口层**|物理传输（网卡、网线、WiFi）|网线、MAC 地址|
- **HTTP / HTTPS** → 第4层（应用层）。定义"请求和响应长什么样"，就是上一讲讲的 `GET /api/users` 那些规则。
- **GET / POST 方法** → HTTP 协议里的一部分，所以也在第4层。
- **DNS** → 第4层（应用层）。它也是个"服务"，只不过任务特殊——帮你把域名翻译成 IP。
- **端口号** → 第3层（传输层）。是 TCP/UDP 用来区分"机器上哪个程序"的门牌号（上一讲讲的那个 443、3000）。
- **IP 地址** → 第2层（网络层）。定位"哪台机器"。
- **TCP 本身** → 第3层。负责"可靠传输"（你之前问过的那张架构表里，增量数据拉取用的就是裸 TCP 二进制流）。

#### 域名
1. 域名（github.com）本质是 IP 的别名，通过 DNS 解析成 IP
2. 端口其实有，只是省略了 —— HTTPS 默认 443，HTTP 默认 80，浏览器自动补上
3. 所以完整写法其实是 `https://github.com:443/Yusiquweierwang/-repo`

**它省略了两样东西：IP 和端口**

`https://github.com/Yusiquweierwang/-repo` 的完整写法其实是：

```
https://github.com:443/Yusiquweierwang/-repo
        └───┬───┘ └┬┘
         域名    端口(默认443)
```

**1. `github.com` 是 IP 的"别名"（域名）**

域名本质是给人看的名字，机器之间通信还是靠 IP。浏览器拿到 `github.com` 后，会先去问 **DNS 服务器**（相当于"电话簿"）：

> "github.com 的 IP 是多少？" → DNS 回答："是 `20.205.243.166` 这种"

然后浏览器再拿这个 IP 去连接。所以**域名 = IP 的可读版本**，你完全可以直接用 IP 访问 GitHub，只是太难记，所以用域名。

**2. 端口省略了，因为 `https` 已经暗示了默认端口**

上一讲说过端口范围 0~65535，但有几组**约定俗成的默认端口**：

|协议|默认端口|说明|
|---|---|---|
|`http`|**80**|普通网站|
|`https`|**443**|加密网站|

浏览器看到 `https://`，就知道"如果没写端口，默认连 443"。所以：

```
https://github.com          =  https://github.com:443
http://example.com          =  http://example.com:80
```










#### URL
**一个 URL 的三段分工**

```
http://localhost:3000 / api / users / 123
└──────┬──────┘    └──┬──┘  └─┬──┘   └┬──┘
   机器 + 端口       前缀    资源    资源ID
```

- `localhost:3000`：找哪台机器的哪个程序（上一讲说过）
- `/api/users/123`：进了这个程序之后，**定位"哪个资源"**
- `GET` / `POST`：**对这个资源做什么动作**

---

**路径 `/api/users` 怎么读**

**`/api` 是"约定前缀"**——意思是"后面是接口，不是网页"。这纯粹是开发团队的命名习惯，没有技术强制力，但大家都这么用，一眼就能区分：

- `/api/users` → 是接口（返回 JSON）
- `/users` 或 `/user.html` → 可能是页面（返回 HTML）

**`/users` 是资源名**，代表"用户"这个资源的**集合**（一堆用户）。

**`/users/123` 代表"编号 123 的那一个用户"**（单个资源）。

所以路径的本质是**名词**：用一串斜杠路径，指向某个具体的"东西"（用户、订单、商品…）。

#### 控制面（信令）走HTTP+JSON，数据面（数据）走TCP+二进制流
**为什么「请求」用 HTTP + JSON**

这个方向的请求内容是：_"给我某个范围的增量网格化数据 + 地图服务地址"_。它是：

- **量小**：就几个参数（范围、网格编号、版本号），几行 JSON
- **控制信号**：是"要什么"的指令，不是数据本身
- **要通用、好对接、好调试**

HTTP + JSON 在这里的优势：

1. **人可读、好排查**：出问题直接看请求体 JSON，一眼看懂在要什么
2. **跨系统、跨语言零门槛**：任何语言、任何框架都能发 HTTP、解析 JSON，方便和第三方平台对接
3. **过防火墙/网关容易**：HTTP 走 80/443 标准端口，CDN、网关、负载均衡全兼容
4. **有现成生态**：重试、鉴权、缓存、日志，HTTP 生态全有


**为什么「增量数据」用 TCP + 二进制流**

这个方向传的是：_低空航图增量网格化数据_。它和请求有本质区别：

- **量巨大**：网格化数据可能是海量的点云、瓦片、高程、纹理
- **是二进制**：数据天生是二进制，不是文本
- **要流式、要吞吐、要低延迟**
