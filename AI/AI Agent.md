








### LLM基础
#### 大模型基础







**1.token**
大模型处理和计费的最小单元，模型读写文本的切片。

关键点：**token ≠ 字，也不等于单词**。它是模型用「分词器（tokenizer）」按某种算法切出来的片段。

举例（英文）：

```
"Hello world"  →  2 个 token（Hello / world）
"unbelievable" →  可能 3 个 token（un / believ / able）
```
常见英文单词会占 1 个 token，但生僻词、长词、带词缀的词会被**再拆碎**。

举例（中文）：
```
"你好"  →  可能 1~2 个 token
"人工智能" →  可能 2~4 个 token
```

+ 分词如何切分
主流模型用 **BPE（Byte Pair Encoding，字节对编码）**。



**2.上下文窗口Context Window**
模型一次能记住的文本量。

 **输入窗口和输出窗口**

|     |    输入窗口（Input）    |  输出窗口（Output）   |
| :-: | :---------------: | :-------------: |
| 含义  |    模型能「读进去」多少     |   模型单次「生成」多少    |
| 数量级 | 很大（128K~1M token） | 较小（几千~几万 token） |
| 例子  | Claude 128K~200K  | 单次输出通常几千 token  |

+ 为什么Agent场景里窗口不够用？
```
Agent 一次任务要装进窗口的东西：
  系统提示词（角色+规则+可用工具清单）  ← 固定占用
  历史对话                            ← 越聊越多
  每一步的「工具调用 + 返回结果」     ← 爆炸式增长
     └─ 比如查了10个网页，每个网页全文塞进来，几万 token 没了
  中间思考过程（reasoning）          ← 部分模型也占窗口
```

+ 上下文管理策略
|策略|做法|效果|
|---|---|---|
|**记忆压缩**|把长历史摘要成几句话，只留摘要|省大量 token|
|**滑动窗口**|只保留最近 N 轮，旧的丢掉|简单粗暴|
|**外部记忆（RAG）**|对话历史存到向量库，需要时再「查回来」|窗口里只放关键信息|
|**裁剪工具返回**|工具返回只保留相关片段，不全塞|避免爆炸|
|**分层记忆**|短期（窗口内）+ 长期（存库）分开|兼顾时效和容量|






**3.推理模型&非推理模型**
**1. 一句话区分**

|      |                  非推理模型                   |                   推理模型                    |
| :--: | :--------------------------------------: | :---------------------------------------: |
| 核心特点 |               **快**，直接给答案                |               **慢**，先思考再回答                |
|  类比  |                   直觉反应                   |                  先打草稿再答题                  |
|  代表  | Claude Sonnet/Haiku、GPT-5.4、Gemini Flash | Claude Opus（深度思考）、o系列、DeepSeek-R1、Kimi K3 |


**4.temperature**
控制模型「敢不敢不走寻常路」。取值范围通常 0~2：

|温度值|效果|适合场景|
|---|---|---|
|0|完全确定，每次答案几乎一样|数学、代码、事实问答|
|0.2~0.5|稳定，基本不跑偏|总结、翻译、Agent 工具调用|
|0.7~1.0|有一定发挥空间|一般对话、内容创作|
|1.0~2.0|放飞自我，越来越「乱」|头脑风暴、创意文案（易出错）|

直觉理解：

```
温度低 = 每次选「最稳」的词 → 安全、无聊、可复现
温度高 = 每次敢选「冷门」的词 → 有趣、有创意、易胡说
```

**关键规律（记这个）：**

- 要**准确**（代码、数学、事实）→ 温度调低（0~0.3）
- 要**创意**（文案、故事、取名）→ 温度调高（0.7~1.2）
- **推理模型**（上一条讲的）→ 通常**强制低温度**，因为思考要严谨，不能让它在推理时「乱想」


**5.Top-p 核采样，Nucleus Sampling**
和温度作用类似，但机制不同。它是「从概率最高的词里，选到累计概率达到 p 为止的那一批，只在这批里抽」。

- top_p = 0.1 → 只在最可能的前 10% 里选 → 很保守
- top_p = 1.0 → 所有词都能选 → 自由

**实际使用建议：temperature 和 top_p 别一起乱调，调一个就行。** 大多数场景只动 temperature 就够了。

类似概念：Top-k

7.参数说明

| 参数                | 作用       | 常用默认值               |
| ----------------- | -------- | ------------------- |
| temperature       | 随机性（最重要） | 0.7（对话）/ 0.2（代码/工具） |
| top_p             | 随机性（备选）  | 1.0（即不限制）           |
| max_tokens        | 输出长度上限   | 按需，工具调用要给足          |
| stop              | 停止符      | 一般不用                |
| frequency_penalty | 防重复      | 0（关）                |




为什么选择ts/ python生态
|语言|传统强项|在 Agent 场景里的意义|
|---|---|---|
|Java|大型企业后端、高并发、稳定性|有用，但太重、迭代慢，适合「成熟后」再重写|
|C++|极致性能、底层|Agent 不需要，性能不是瓶颈|
|C#|Windows 生态、游戏(Unity)|边缘场景，生态没起来|

它们的**强类型、编译、严格工程规范**，在企业级「稳定运行」里是优点，但 Agent 目前处于**快速试错、频繁迭代**阶段，要的是「今天想到今天就能跑」，Python/TS 的动态性和生态广度更合适。
