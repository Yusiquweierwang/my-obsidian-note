
### 第一层：不补会死的（AI 替代不了的基础判断力）

**JavaScript 深度理解**

不要"会用就行"，要到"看到一段代码就知道哪里会出问题"：

|要搞懂的|为什么|
|---|---|
|闭包和作用域链|useEffect 为什么拿到的 state 是旧的，靠的就是这个|
|事件循环（event loop）|异步 bug 的根源，promise/async/定时器谁先执行|
|原型链和 this|Cesium 内部大量用 prototype，看不懂源码你就永远只能抄|
|引用 vs 值|状态管理里最常犯的错|
|内存管理|Cesium 3D 场景动不动几百万个点，不懂这个页面卡死你不知道为什么|

**验证标准**：Cesium 源码随便打开一个模块，能看懂大概在干什么。

**CSS 核心原理，不是属性大全**

| 要搞懂的                    | 为什么                |
| ----------------------- | ------------------ |
| 盒模型                     | 排版的基本单位            |
| 层叠上下文（stacking context） | z-index 为什么不生效     |
| BFC（块级格式化上下文）           | margin 塌陷、float 清除 |
| 包含块（containing block）   | position 的参照系到底是谁  |
| Grid + Flexbox 的布局思维    | 布局就这两，其他都是补充       |
|                         |                    |

**验证标准**：看到一个设计稿，脑子里能直接拆成 CSS 结构。AI 写了布局代码，你能一眼看出为什么不对。

### 第二层：决定你值不值钱的（领域深度 + 工程能力）

**Cesium / 3D 可视化底层**

你已经会用了，补的是"为什么"：

|要搞懂的|为什么|
|---|---|
|3D 图形学基础（矩阵变换、相机模型、坐标系）|Cesium 所有操作都是数学变换|
|Cesium 的 Entity vs Primitive 区别和性能取舍|大规模场景的命门|
|3D Tiles 数据格式和加载机制|BIM 模型导入必须搞这个|
|WebGL/GLSL 基础|自定义效果、性能优化|
|坐标系统转换（WGS84/CGCS2000/地方坐标系）|GIS 行业的硬骨头，AI 数据很少|

**TypeScript**

React 和 Cesium 都重度用 TS。关键是：

- 不是"会写类型注解"，而是**会设计类型**——什么该抽象成 interface，什么用泛型
- 你的 cesiumDemo 从 JS 改成 TS 本身就是一个好的学习路径

**工程化的基本概念**

你提到的 Docker 在这层：

|概念|你需要的程度|
|---|---|
|模块化、打包（Vite/Webpack）|能配，能排错|
|Git 工作流（rebase、cherry-pick、冲突解决）|熟练到不害怕 merge|
|CI/CD 基本概念|知道流水线在干什么|
|Docker|能给自己的项目写 Dockerfile + compose|
|Node.js 基本能力（fs、path、stream）|脚本处理 BIM 数据，这个需求很常见|

### 第三层：决定天花板高度的（不急，但要知道方向）

|领域|跟你有什么关系|
|---|---|
|**BIM/GIS 行业知识**|IFC 格式、LOD 概念、坐标系、BIM 交付标准——这些是 AI 训练数据极度匮乏的，也是你区别于普通前端的壁垒|
|**软件架构基础**|不是写一个组件，是设计一整套系统怎么拆——Electron 的 main/renderer 进程、插件架构、数据流设计|
|**算法与数据结构基础**|空间索引（四叉树、R-tree）、可见性裁剪——Cesium 内部就在用，懂了才能优化大规模场景|

### 两周一循环的学习节奏建议

既然你现在白天有闲：

```
上午（公司时间）：
  做 cesiumDemo 的深入改造 → 顺便看 Cesium 源码 → 记下不懂的点

下午（公司时间）：
  补一个具体知识点 → 直接在你的 demo 里验证 → 而非只看不写

晚上/周末：
  做之前聊的 GitHub 小工具 → 把学到的 JS/TS/React 在真实项目里用出来
```

关键原则：**每一个知识点，都必须在你自己的项目中落地过。** 看过 ≠ 会了，会在项目中用出来 = 会了。
